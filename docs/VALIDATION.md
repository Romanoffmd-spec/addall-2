# AddAll 2.0: материалы по проверке системы (черновик валидационного пакета)

Версия документа: 25.11.2026. Статус: рабочий черновик, не формальная валидация.

Документ описывает, какие требования к системе проверяются и чем. Он нужен как основа для формальной валидации компьютеризированной системы по риск-ориентированному подходу (ICH E6(R3), раздел о компьютеризированных системах; подход GAMP 5). Формальная валидация требует утверждённого плана, протоколов испытаний с подписями, отчёта и контроля изменений: этого пока нет.

## 1. Назначение системы и границы

- Назначение: ведение клинических регистров и аудита качества (сбор данных по эпизодам лечения, наблюдение, контроль полноты, показатели качества, отчёты за период).
- Не предназначена сейчас: для клинических исследований под надзором регулятора (FDA, EMA), для принятия решений о лечении конкретного пациента, для хранения реальных персональных данных в онлайн-демо.
- Версии: браузерная (данные в браузере), онлайн-демо (облако за пределами РК, только вымышленные данные), серверная (Node.js + SQLite на сервере учреждения).

## 2. Требования и проверки (трассируемость)

Автоматические проверки лежат в `dev-tests/`. Запуск: `python dev-tests/run.py` (браузерные сценарии), `node dev-tests/stats_check.js` (статистика), `node dev-tests/server_check.js` (сервер), `node dev-tests/load_check.js` (нагрузка). Каждый браузерный сценарий завершается проверкой отсутствия ошибок в консоли.

### 2.1 Целостность данных и журнал аудита
| Требование | Проверка |
|---|---|
| Каждое изменение записи пишется в журнал: кто, когда, старое и новое значение | e2e, t26, t27, t35, t37 |
| Изменение сохранённой записи требует причины, причина в журнале | t26 (форма события), t37 (карточка пациента) |
| Изменения вне полей формы (ФИО, даты, статус) тоже попадают в журнал | t37 |
| Конфликт одновременных правок не теряет данные | server_check (устаревшая ревизия) |
| Выпущенный отчёт за период не изменяется; исправление только новой версией с объяснением | t25, server_check (неизменяемые выпуски) |
| Сверка с первичной документацией и блокировка записи | t8, t15 |

### 2.2 Доступ и безопасность
| Требование | Проверка |
|---|---|
| Роли и права; доступ к регистру по отделению и учреждению | t6, t15, t16, t30, server_check |
| Блокировка после 3 неверных паролей, завершение сессий при смене пароля | t15, server_check |
| Хэширование паролей (scrypt) и миграция старых хэшей | server_check |
| Двухфакторный вход TOTP (RFC 6238), запрет повторного кода, сброс администратором, ключ не уходит клиенту | server_check |
| Закрытые вложения недоступны без прав | server_check |
| Обезличенные выгрузки: идентификаторы и чувствительные поля исключаются | t31 |
| ID пациента: формат с контрольным знаком, один ID на один ИИН во всех регистрах, не меняется, чужой ID не принимается | server_check, t39 |
| Роли: исследователь получает только обезличенные карточки и не видит документы; орган здравоохранения и фарма не получают данных пациентов; ИТ-администратор не видит медицинских данных и не создаёт администраторов; руководство учреждения не меняет записи | server_check, t39 |
| Заявки на данные: подача, рассмотрение, неизменность текста заявки после подачи | server_check, t39 |

### 2.3 Полнота и качество данных
| Требование | Проверка |

| Требование | Проверка |

## 3. Нагрузочная проверка серверной версии (25.11.2026)

`node dev-tests/load_check.js N` создаёт временную базу с N пациентами и 4N событиями в 5 учреждениях, включает изоляцию по учреждению и замеряет время на одном компьютере.

| Объём | Чтение всех пациентов (админ) | Чтение всех событий (админ) | Чтение событий врачом своего учреждения | Запись события, медиана / 95% |
|---|---|---|---|---|
| 20 000 пациентов, 80 000 событий | 0,16 с | 0,6 с | 1,0 с | 1 мс / 2 мс |
| 100 000 пациентов, 400 000 событий | 0,8 с | 3,3 с | 5,9 с | 1 мс / 3 мс |

С 25.11.2026 (вечер) клиент серверной версии загружает список целиком один раз, дальше только изменения; ответы сжимаются. 20 000 пациентов и 80 000 событий: первая загрузка событий врачом 0,9 с, догрузка изменений 2 мс.

Вывод: запись быстрая, повторные чтения почти мгновенные. Первая загрузка и расчёт показателей на клиенте для национального масштаба (сотни тысяч случаев на одного пользователя) остаются задачей до национального развёртывания: расчёт показателей на сервере.

## 4. Известные ограничения (что не валидировано)

- Нет формального плана и отчёта валидации, подписей и контроля изменений по процедуре.
- Нет электронной подписи под записью (в Казахстане естественно делать через ЭЦП).
- Нет внешней проверки информационной безопасности и аттестации по требованиям РК.
- Точность приёма документов на реальных выписках не измерена.
- Пропуски данных: анализ полных случаев, множественной импутации нет.
- Удобство не проверялось на реальных пользователях.
- Онлайн-демо хранит данные за пределами РК и не подходит для персональных данных.

## 5. Порядок изменения системы

Каждое изменение: описание в `HANDOFF.md` (журнал изменений), прогон всех автоматических проверок, запись результата. Публикация онлайн-версии только после прогона. Для формальной валидации этот порядок нужно оформить процедурой с ответственными и подписями.
